# PR #7 Review — "feat: read user-set session names from Hermes Agent"

Review seat: the fleet's available. Scope: `ryanlewis/herdr-workspace-renamer` PR #7 (base `main`, head `feat/hermes-provider`, 1 commit, +320/−3), read whole from `/tmp/pr7.diff`. Register: humble, the PR's service.

## Strengths

- The provider's contract is exactly right: `load` returns `None` when it has nothing to say, and every failure mode — missing file, absent `profiles/`, corrupt/truncated DB, schema without `sessions`, a row that will not decode — collapses to "no session info here" rather than an error. The `let Ok(...) else { return Vec::new() }` ladder is the correct shape for a sweep that must never disturb a live agent.
- The read-only discipline is real, not decorative: `OpenFlags::SQLITE_OPEN_READ_ONLY`, a narrow `SELECT id, title`, and a docstring that names the multi-GB WAL and the never-block-or-mutate rule. The `title_source = 'user'` filter is the right signal — the only user-set provenance — and it keeps the adapter from chasing the agent's own `llm`/`derived` retitling.
- The profile scan is deterministic: default DB first, then named profiles sorted, with `names.entry(id).or_insert(...)` making "first wins" independent of `read_dir` order. `hermes_default_profile_wins_a_duplicate_id` pins that.
- The tests are honest about the fake schema and cover the label-chasing guard well: `llm`, `derived`, NULL source, empty string, and NULL title are each asserted as no-opinion.

## Correctness findings

1. **The join key is the one open item, and the code's own docstring is where the risk lives.** The provider keys `Names` on the DB's `id` (timestamp-style, e.g. `20260904_184555_4ad7e4cc`) and asserts that this is "the session id herdr gets from the hermes integration's `pane report-agent-session` call." The real `sessions` table also carries `session_key` (platform-style, e.g. `agent:main:...`), and the herdr-side token's space is unverifiable from this host. If the integration reports `session_key`, every Hermes lookup misses silently and the provider is a no-op — no error, no log, no test failure, because the fake schema has no `session_key` column. Suggestion: key the map by both `id` and `session_key` (with `id` precedence, since it is the primary key and what `hermes sessions rename` operates on), or emit a diagnostic when a pane token matches neither, so the mismatch is observable rather than silent. At minimum, a test with a `session_key` column and a pane token in that space would force the decision.
2. **`rows.filter_map(Result::ok)` is a second silent-drop path.** A schema variant where `id` or `title` is not TEXT (e.g. an INTEGER id) would drop every row and look exactly like "no user-set titles." The "no session info here" contract is preserved, but the failure is indistinguishable from an empty result. Suggestion: on a row-decode failure, return an empty vec for that DB (or count the drop) so schema drift is at least debuggable; the current shape is fine for the real DB, where both columns are TEXT.
3. **The query itself survives both schemas.** It references only `id`, `title`, `title_source`, all present in the fake `CREATE TABLE` and in the real DDL (which adds ~50 more columns). The `title IS NOT NULL AND title <> ''` guard is redundant-but-harmless (the `IS NOT NULL` makes the `<>` non-NULL), and `title_source = 'user'` is exact and case-sensitive, matching the real lowercase values.
4. **The profile-scan ordering matches the docstring.** `profiles.sort()` on `PathBuf`s under a shared prefix is alphabetical by profile name, and the default DB is pushed first. One nuance: the sort is on the full path, and no test exercises two named profiles — only one is scanned. A two-profile test would make the "alphabetical" claim load-bearing.

## Edge-cases

- **NULL and empty titles:** excluded by `title IS NOT NULL` and `title <> ''`; both tested (`local-null`, `local-blank`). Good.
- **WAL-read concurrency:** the read-only open is the right instinct, but `SQLITE_OPEN_READ_ONLY` alone does not guarantee a lock-free read. A WAL-mode DB whose `-shm` is absent and whose directory is not writable can fail the open (SQLITE_CANTOPEN/READONLY); a rollback-journal DB under a writer can return SQLITE_BUSY. The code handles both as no-opinion, which is safe, but no test exercises a live WAL or a busy writer — the "unreadable" test writes garbage, not a hot WAL. Suggestion: a test that creates a WAL-mode DB, holds a write transaction, and asserts the sweep still returns the committed user-titled row (or returns cleanly) would pin the rationale.
- **Schema-variant tolerance:** the fake schema is minimal (`id`, `title`, `title_source`); the real table has `session_key`, `runtime_revision`, `source`, and dozens more. The query survives because it names only three columns, but no test proves that against the real DDL. Suggestion: one test that creates a representative real `sessions` DDL and asserts the query still returns the title.
- **Multi-profile collisions:** the `id`-collision test is good (default wins). The untested corner is a `session_key` collision across profiles — if the join ever moves to `session_key`, the default-first rule could apply the default profile's title to a named profile's pane. Worth a comment or a test if the key broadens.
- **Fallback when the provider returns nothing:** `load` returns `None` on an empty map, and the README says the terminal title is used instead. The tests call `lookup` directly and do not exercise the registry-level fallback for a Hermes pane with only `llm` titles. Suggestion: one adapter-level test asserting the terminal title wins when the provider has no user-set name.
- **Missing `profiles/` with a present default DB:** handled by the same `Err(_) => Vec::new()` arm as a missing home; not explicitly tested, but the code path is shared.

## Tests' coverage + spec-seed

What the tests prove: a user-titled session joins; `llm`/`derived`/NULL-source/empty/NULL titles are ignored; a named profile is scanned; the default profile wins an `id` collision; a corrupt DB, a schema-less DB, and a missing home are all silent. What they leave open: the join-key space, the real schema, the WAL/busy-writer path, the two-profile ordering, and the registry-level fallback.

Three highest-value additional cases:

1. **Join-key space (`session_key`).** Shape: a DB with the real `id` + `session_key` columns; one row with `id = 20260904_184555_4ad7e4cc`, `session_key = agent:main:...`, `title = "user title"`, `title_source = 'user'`. Assertion: `lookup(&home, "hermes", "agent:main:...")` returns `Some("user title")` if the integration reports `session_key` (or, if the intended key is `id`, assert `None` plus a diagnostic so the choice is explicit). Value: this is the one open item from the rig's verification; it converts a silent no-op into a pinned contract.
2. **Real-schema tolerance.** Shape: `CREATE TABLE sessions` with a representative real DDL (`id TEXT PRIMARY KEY`, `session_key TEXT`, `runtime_revision INTEGER NOT NULL DEFAULT 0`, `source TEXT NOT NULL`, `title TEXT`, `title_source TEXT`, …) and one user-titled row. Assertion: `lookup` returns the title. Value: proves the query survives the real DB, not just the minimal fake — the fake-schema test's `CREATE TABLE` omits columns the real table has.
3. **WAL-mode read-only concurrency.** Shape: create the DB, `PRAGMA journal_mode=WAL`, insert a committed user-titled row, then hold a write transaction open on a second connection while calling `lookup`. Assertion: the lookup returns the committed title without blocking or erroring (or returns `None` cleanly if the read-only open cannot proceed). Value: pins the read-only rationale against the real multi-GB WAL DB, which no current test exercises.

Runner-up: the registry-level fallback — a Hermes pane with only `llm` titles should fall back to `terminal_title_stripped`; the provider's `None` is tested, the adapter's use of it is not.

## Verdict

The PR is close: the contract, the read-only discipline, and the label-chasing guard are right, and the tests are honest. It becomes a thing when the join key is pinned to the token the herdr integration actually reports — key on `id` and `session_key` (or log the miss) and add the session_key test — so a space mismatch is a failing test rather than a silent no-op.
