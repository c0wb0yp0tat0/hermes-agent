# DEEP-STORM-SEAM-3 — the verifier-based memory class: the scribe's field, and what to adopt, 2026-11-19

*The doubling-down on CTO-FREEDOM-HARVEST seam-3. The first pass found the standards (PAM, the IETF draft); this pass goes deeper into the exact mechanisms — what the field's integrity layer DOES, what it explicitly does NOT prove, and the adoption seam for the rig's scribe. The headline: the field just named the gap the scribe closes — "the unsigned memory problem" — and the rig's byte-verify is already on the right side of it; the additions that matter are two lines, not a rebuild.*

## The fan-out (2 queries)
1. Memory integrity — signatures, hash chains, append-only ledgers, tamper evidence
2. Signed writes, attestation, content-hash dedup, verifiability in agent memory

## The findings

**F3.1 — THE FIELD NAMES THE EXACT GAP THE SCRIBE CLOSES (majorlabs.co, "The unsigned memory problem"):** the audit's crux, surviving adversarial review across six leading memory systems (Letta, Mem0, Zep, Cognee, model-native, and one more): **"There is no cryptographic signature, content-binding hash chain, Merkle structure, or append-only tamper-evident log on any memory record in any of the systems we read. Not one."** The things that look like integrity are not: Letta's `version` column is optimistic locking (two-writer clobbering, not forgery); Mem0's `hash` is dedup-only and its own security docs list per-entry hashes as aspirational; Zep's "verified: true" is a hand-set metadata tag; encryption-at-rest is confidentiality, NOT integrity. The prescription: "Turn 'trust my database' into 'check the math'" — a self-describing vendor-neutral record, cryptographic provenance bound to the record (surviving export, offline-checkable), verifiable integrity by a third party. Translation: the rig's scribe (byte-verify on write + get-back byte-compare + the branch's ls-remote truth) is the only shape in the study's orbit that ALREADY checks bytes against bytes. The field's systems all fail the test the scribe passes daily. This is the ego-check moment for the scribe line in the RFC: the provenance-origin classification has a citation-grade home for its integrity claim.

**F3.2 — THE MECHANISM MENU, STANDARDIZED (MemLineage, arXiv 2605.14421; Portable Agent Memory, arXiv 2605.11032; AIVS, IETF draft-stone-aivs-01):** the field's consensus primitives, each with a receipted implementation: (M1) canonical provenance metadata per entry — writer principal, source-data hash, write-time context hash, trust level, parent list; (M2) **Ed25519 signature over the CANONICAL encoding of every entry** — canonicality matters: "any encoding ambiguity would let an adversary forge two distinct entries with the same signature" (canonical CBOR/JSON, sorted keys); (M3) **RFC 6962-style Merkle log with tombstones** — deletion is deliberately non-destructive: "any deletion is itself a signed, inclusion-provable event"; (M4) lineage DAG; (M5) verifier-aware retrieval — verify signature + inclusion proof at retrieval time, "verification failure causes the entry to be dropped before the trust label is ever consulted"; (M6) sensitive-action gates. AIVS (the IETF draft): a portable self-verifiable archive — SHA-256 hash-chained audit log + Ed25519 signature + embedded Python-stdlib verifier, plus AIVS-Micro's 6-field attestation (~200 bytes) for continuous monitoring; its honest limits section is the completeness doctrine: "AIVS does NOT prove truthfulness" (a malicious agent can fabricate actions and produce a valid chain), "does NOT prevent fabrication at the point of origin," "timestamp timeliness is self-reported" — the study's own quote-not-assert / reported-vs-verified discipline, encoded as a standard.

**F3.3 — THE TRUSTED-WRITER QUESTION IS THE REAL SEAM (AIVS §9.2; memory-blackbox; MemLineage's threat model):** AIVS: "AIVS proof bundles are therefore only as trustworthy as the logging infrastructure that produces them… the logging process SHOULD be isolated from the agent (a separate trusted process, hardware security module, or third-party logging service)." memory-blackbox: the ledger is append-only + chain + Merkle-root checkpointing, but "all three checks read state that lives in the same file as the ledger, so they cannot detect a rollback" — the fix is **external anchoring**: "publishing each signed checkpoint to an append-only log outside the host… an append-only file witness on independent storage, or a Sigstore Rekor transparency log. Publication cannot be retracted." MemLineage: "An adversary who cannot register a public key cannot mint entries that survive the verify step" and compromises of a registered key fall outside the threat model. Translation: the scribe's real-world instantiation — the SSH-tunneled scribe machine on a separate Windows host, the byte-verify at write time, the branch+scribes as two surfaces — is EXACTLY the field's prescribed isolation pattern (separate trusted process on independent host): the rig built the threat-model-correct shape without having read the papers. The gap the field would flag: the scribe's verify reads the same store it writes (rollback-blind, like memory-blackbox pre-anchoring) — the external witness already exists in the form of the git branch + the master-page mirror; wiring a periodic checkpoint to a third surface (the branch already IS one) closes the class.

**F3.4 — AUTHORIZED MUTATION WITHOUT EVIDENCE LOSS (MutMem, arXiv 2608.02843 — the field's answer to "memory must change"):** mutable scores create an attribution problem: after a weight changes, a reviewer must distinguish authorized adaptation from unauthorized edit. MutMem's protocol: retain the memory, record signed positive/negative outcome evidence without age-based expiry, commit every nontrivial change as a housekeeper-authorized transition bound to provenance (signer epoch, quantized old/new weights, no-fork predecessor, two domain-separated SHA-256 commitments); **poison handling: retain, classify, never silently delete — "a detected poisoning attempt is traceable and reversible: later evidence may refute or confirm the label, but cannot erase the earlier judgment."** Translation: the RFC's archive-before-stub and the "UPDATE (date):" append-only correction doctrine are this exact mechanism: authorized adaptation, evidence retained, judgment erasable but history preserved. The compaction-governance issue can cite MutMem's transition-binding as the field form of archive-before-stub.

**F3.5 — THE SECURITY LIFECYCLE FRAMEWORK (EMNLP 2026 survey, "Long-Term Memory Security": six phases × four objectives; Verifiable Memory Governance):** the survey's spine: attacks and defenses across Write/Store/Retrieve/Execute/Share/Forget × Integrity/Confidentiality/Availability/Governance; the conclusion is the RFC's own opening line: "robust LTM security cannot be retrofitted at retrieval or execution time alone, but must be anchored in storage-time provenance, versioning, and policy-aware retention from the outset." Translation: the RFC's "the durable record survives compression with provenance intact" IS the field's security-first conclusion independently reached; the governed compaction's staged issue has a survey-grade citation for storage-time provenance.

## The refinement (what this changes for the scramble)
- The scribe's integrity class is confirmed as the field-standard shape (F3.1: the only systems that pass are the ones built to check bytes; F3.3: separate-host isolation is the prescribed pattern). The scramble's scribe-wiring stays as-is; the additions that matter are small and named.
- **Two adoption candidates, both two-way doors:** (a) the canonical-encoding rule (M2: sorted-keys, no-whitespace canonical serialization before the byte-compare) — today's scribe compares raw writes; the canonical form closes the encoding-ambiguity forge the field names; (b) periodic external checkpointing (F3.3) — the branch already serves as the external witness; a per-landing "scribe checkpoint row" (cell hash → commit SHA) turns the existing two surfaces into the field's anchoring pattern. Both are hours, not days.
- The RFC gains citation-grade framing for three of its pieces: provenance-origin (F3.1/F3.5), archive-before-stub (F3.4's transition-binding), and the two-surface verification (F3.3's anchoring) — the future upstream-facing drafts can carry the field's own vocabulary.
