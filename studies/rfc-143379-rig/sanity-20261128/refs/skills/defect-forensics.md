# Defect Forensics (root-cause hunt upstream)

When a cluster of observed platform/product failures feels like ONE systemic issue rather than isolated bugs, investigate the vendor's public tracker to find the parent class before concluding or reporting. The user's recurring question: "are we overlooking the real parent ticket? is my read wrong?" Adjudicated verdict + evidence, not a dump.

## Procedure

1. **Enumerate the defect CLUSTER from your own primary evidence first.** List each distinct defect you actually observed (truncation, flag ignored, results lost, budget not enforced, config dropped) with its primary source (your log/file:line). These named defects are the search keys — do not search on the user's summary sentence alone.

2. **Map each observed defect to tracker terms and search the repo:**
   ```
   gh search issues "<symptom-term>" --repo <owner>/<repo> --limit 15 --json number,title,state,createdAt
   ```
   Read the bodies of the strongest 3-6 per defect (`gh issue view <n> --json body,labels,comments`). Note state, labels (esp. `duplicate`), createdAt, assignees. `gh api search/issues` returns 404 — use `gh search issues`.

3. **Hunt for the parent class/umbrella.** Search terms: `umbrella`, `one bug class`, `one defect`, `epic root`, `parent`. Repos under load accumulate umbrella issues (maintainers file them when a per-key fix policy defaults to patching one site at a time). A real umbrella enumerates N open instances and names the shared mechanism. Multiple independent reporters hitting the SAME file/surface = one class, even if each filed a distinct ticket.

4. **Date-stamp EVERYTHING.** Record first-observed date of each observed defect AND createdAt of each candidate issue. Correlate against product-change events (big refactor, release, provider change) from the vendor's announcement posts. **Root vs amplifier:** defects whose tickets PREDATE the change event are the root class; the event (e.g. a 34% LOC refactor) is the amplifier/re-exposer, not the cause. Give both read and say which is which — a clean temporal correlation is evidence, not proof of causality.

5. **Check fix velocity, not just existence — via the MERGED-PR stream, not the per-ticket cross-references.** "Checked" on a repair-campaign/tracking issue means a PR was PREPARED, not merged. Pull the actual merge state before claiming a fix exists. The reliable query (per class term):
   ```
   gh search prs "<class-term>" --repo o/r --merged --merged-at >=<event-date> --json number,title,closedAt,author
   ```
   Filter merged-by-date on `closedAt` (NOT `mergedAt` — that field is unavailable on `gh search prs`).
   **OPEN ticket ≠ unfixed class.** A defect ticket can stay OPEN with its linked fix-PRs forever unmerged while maintainers fix the CLASS under unrelated salvage PRs ("salvage #N") that never cross-reference the issue. Per-ticket OPEN is a misleading measure of "still broken" — search the merged stream for the class terms since the amplifier event and read the fix-share. The verdict that matters is class-fix velocity, not the six individual ticket badges.
   **Read the AUTHOR of the merged stream, not just the count (binding, earned 09-21):** a fix wave dominated by ONE committer is a single-dev salvage campaign — and when that author is also the author of the amplifier event (the refactor), the picture is coherent: the person who changed the shape is the person repairing it, at a velocity nobody else matches. Name that in the report — it converts "amid-the-fix" from a count into a characterization (one-man repair wave by the man who caused the wave) and sets expectations about pace and bus-factor. A spread of authors across the merged stream is a different signal (institutional repair); a single author is a personal campaign.

   **Classify the merged stream by SURFACE as well as by author.** Pull the latest N merged PRs (`gh search prs --repo o/r --merged`, map by surface from the titles) and bucket them: latent-class fixes (state/lock/update/compaction/gateway), catalog/plugin churn ("add X to catalog", bumps), polish/l10n. The concentration ratio answers "who is actually carrying the class, and is the crowd playing elsewhere?" — e.g. a stream where 8-of-8 latent-class fixes are one author while 15 catalog PRs come from ~9 one-off contributors undermines the naive "everyone is contributing" read. Name the concentration explicitly.

   **Test the POSTURE behind the author, don't assume hierarchy (binding, earned 09-23):** "founder accumulating team wins" and "hands-on implementer" are distinguishable from the STREAM, not the org chart — org-membership API calls 403 without `admin:org`, so use what the stream shows: (1) who MERGES the author's PRs: `gh api repos/O/R/pulls/N --jq '[.user.login, .merged_by.login]'` — merged_by == author means self-merge, no independent eyes on that gate, which sharpens bus-factor (sole implementer + sole merger = the class lives or dies with one person's availability); (2) authorAssociation on a merged search (COLLABORATOR vs MEMBER vs CONTRIBUTOR); (3) commit share via `repos/O/R/contributors` — an author at 5x the next contributor wrote the code themselves, the opposite of a green-light-only leader; (4) tenure vs the amplifier — an earliest commit predating the refactor means the repairer predates the damage. If the credit flow the user assumed is inverted (the wins are the author's own labor, not borrowed), say so plainly.

   **Separate AUTHORSHIP from COMMITTERSHIP — the byline surface is not ownership (binding, earned 09-24):** a GitHub commit carries two names: the AUTHOR (whose work the commit represents) and the COMMITTER (whose account landed it, typically through the merge). A founder's name riding the committer line on nearly every commit is the platform's one-name-per-PR design, not evidence he wrote it; conversely a name on the author line is his own labor until the census proves otherwise. The question "who actually did the work" is answered by splitting the two axes over the FULL range — `gh api repos/O/R/compare/<base>...<head>` caps its `commits` array at 250 even when `total_commits` is larger, so page the commits endpoint (or `per_page`) for the true count, then split author vs committer and count distinct author emails under one byline. The decisive credit-hygiene signal is the `chore: map <email> → <login> for attribution` commit class — each one re-attributes a contributor email to its human, and a cluster of them under the byline that appears to dominate INVERTS a "credits are hoarded" read: the name on everything is actively giving credit away. Say so plainly. Also: merge commits carry the MERGER's name, sometimes a different person than the PR author — a merge-commit name is a routing artifact, never an authorship claim.

   **Verify the VEHICLE of a cited number before claiming "fixed by #N" (binding, earned 09-21):** a commit message that references a number in its subject ("fix(cli): honor --resume in one-shot mode (#105892)") is NOT evidence that number is a merged PR — it may be the bug-issue the commit addresses, and the issue can remain OPEN despite the fix landing on main. Before any "fixed by #N" claim, run `gh pr view N` (fails = not a PR) AND `gh issue view N` (state + title). A commit on main + a closed bug-issue number in its message + the defect issue still OPEN is the mis-attribution trap: the technical fix exists, the attribution doesn't. The fix commit is real; the vehicle label is wrong. This is exactly the claim a maintainer will check first.

   **Recover the REAL fixing PR from the commit, don't stop at "not a PR" (binding, earned 09-21):** when the cited number is NOT a PR, the investigation is only half done — the fix commit still has a vehicle, and it is findable. `gh api repos/O/R/commits/<sha>/pulls` returns the PR(s) the commit landed through (works for squash-merged commits; the PR shows "Merged via #N" on the commit page). Cross the PR's merged_at against the bug-issue's closedAt: closedAt == merged_at + ~1s means the issue was closed BY that merge — the definitive vehicle proof. A self-correction that names the negative ("#105892 is not a PR") without naming the real PR invites the maintainer's first check to out-know the correction; name the vehicle and the correction becomes airtight. Also check whether the defect issue has EVER been referenced by any PR/commit (`git log --all --grep=<N>` + the issue timeline) — a defect that no fixing PR references is a genuinely open ask, not a closed one.

   **An OPEN fix PR is not evidence the class "is being worked" — check its base still exists (binding, earned 09-21):** a PR opened against a code shape that a later refactor deleted is stale and conflicting, not active work. Before citing open PRs as proof a class is being addressed, verify (1) the PR's last commit date vs the refactor date, (2) whether the function/line the PR's diff mutates still exists on current main (`git log -S '<symbol>'` to date the refactor; grep the clone for the old symbol), and (3) mergeable/mergeStateStatus (UNKNOWN after a refactor = never recomputed). Two "open fix PRs" that predate a `cmd_remove` refactor and target a deleted `_display_removed` are orphaned evidence — the honest contrast is that BOTH the class and its fix PRs are unworked. A hostile maintainer's first pushback is "reopen these against current main before claiming the class is being worked."

6. **Verify the vendor's own claims against primary sources.** The announcement post is context, not truth. Cross the post text against the tracker and independent coverage. If the vendor's own writeup admits regressions shipped (removed public names, changed exception handling, fixed post-merge), that is the amplifier evidence you cite. A third-party coverage URL cited in a brief can 404 even when the facts hold — the vendor's own post is the source, name it and drop the dead citation.

7. **Pin the USER's OWN build before correlating (the falsifier).** "Your build predates/contains the change" is testable, not guessable: `hermes --version`, then `git merge-base --is-ancestor <merge-commit> HEAD` in the install's repo. A shallow clone makes is-ancestor return false spuriously — `git fetch --deepen=3000 origin main` first (read-only, no working-tree change), then re-check. Not-ancestor = the correlation collapses and the event is coincidental; ancestor = the user runs the changed tree and the correlation survives. This one check decides which framing the report gets.

   **The compare-API "ahead_by" misread (binding, earned 09-21):** `gh api repos/O/R/compare/<sha>...main` returning `ahead_by=N, behind_by=0` does NOT mean the commit is absent from main — it means main has grown N commits PAST that commit, i.e. the commit is an ANCESTOR of main (fully contained, `behind_by=0` proves it). A lane that reads "ahead by 6907" as "not on main" produces a false blocking finding that contradicts the merge-base truth. The authoritative on-main check is always `git merge-base --is-ancestor <sha> origin/main` (exit 0 = on main); treat any compare-API reading that contradicts merge-base as the API being misread, and re-verify with merge-base before accepting a "not on main" finding.

8. **Report with the verdict frame.** Verdict (root + amplifier + true parent ticket candidates) → evidence (each claim traced to tracker issue/PR or post) → one next action (usually: pull merged-PR list since the change to measure fix velocity). No defense, no hypothesis-adoption.

   **Return the user's own thesis as THEIR read, confirmed — never as your finding or your correction (binding, earned 09-23).** When verification confirms a hypothesis the user already stated, frame it as "that's your read, confirmed against the record," not "my honest correction of your guess." Repackaging the user's position as the agent's finding is misattribution dressed as analysis, and the user hears it immediately ("this is not a correction if it's what I've been trying to tell you"). Confirm-with-attribution is the move; claiming the insight is the failure. The verbatim-read test: if every clause of your "findings" was already in the user's message, you are confirming, not correcting — say so.

## Pitfalls

- **The installed tree is the byte-truth for runtime-variant claims — the host's repo clone can lie.** 'Which spec/variant does the layer ACTUALLY run' (a lock-holding vs atomic-rename read, whether an action is registered) is answered in the INSTALLED package's bytes, never the study/repo clone (a different ref, ahead or behind the runtime — the tracking ref can lie too). `hermes --version` names the "Install directory:"; grep THERE: `grep -n "_file_lock(" <install>/tools/*.py` classifies the lock shape (only the definition + the write path = rename-safe; the read body inside the lock = lock-holding), and the tool map + action enums show what the runtime registers. Registration in the runtime ≠ exposure in the session: check the session's OWN tool schema before claiming the agent can or cannot call the action — a session that never receives the action reads invoked-count 0 while the store answers fine.
- **A symbol-count drop across a refactor is a FILE-SPLIT hypothesis first, a removal hypothesis second — verify the moved-to file and the CALLERS before concluding a compensation was removed.** When a refactor shrinks a file's symbol references (e.g. `read` refs 65 → 5), the naive read is "the mechanism was removed." The correct first check is whether the code MOVED: `git show <post>:<file>` for the moved-to module (a store split into `memory_tool_store.py` carries the read-safety layer intact), then `git grep` the CALLERS (`format_for_system_prompt` still invoked by system_prompt.py/context_breakdown.py = the read path survives). A count drop caused by a file split is a false alarm; concluding "compensation removed" on the count alone sends the investigation down a dead end and mis-frames the verdict. The real question is always behavioral: does the model still get the read path, at the same fidelity? (Earned 10-02: the shrink's 65→5 read-ref drop was the store split; the system-prompt injection, drift guards, and success-response all survived — the honest verdict was "the shrink's sin was not removing the compensation, it was not VERIFYING the compensation still worked.")
- **Before re-deriving a finding, search the workspace for the user's own prior kaizen/investigation layers — the user runs kaizens on everything and the artifacts are on disk.** A weeks-long investigation accumulates a sprawl of artifacts (A3 plans, latent maps, verification waves, timeline studies, presentation folders). Re-mining git history or re-running queries when `SHRINK-KAIZEN-PRESENTATION/`, `SHRINK-VERIFICATION-WAVE/`, or a `*-TIMELINE-STUDY.md` already exists on disk is pure waste and reads as not knowing the rig. Search first: `find /root/workspace -iname "*<topic>*"` + grep the drop folder for the class terms, read the verdict documents cold, and only then extend — never re-derive. The user's own framing: "you're redoing a lot of work that's actually on disk." (Earned 10-02: the shrink root-vs-amplifier question was already adjudicated in the A3 + latent map; the head re-mined git for an hour before finding them.) When an assessed tool (a tracker, a report, a generated digest) is missing an item it should contain, check whether the committed output was produced from a fixture or a live run before concluding the code can't see it: read the generator's discovery/filter logic AND execute it read-only against current data (a `--check`/dry mode if present). A fork-sourced PR absent from a committed tracker can be a stale fixture (`related: []` in the fixture JSON) while the live code path discovers it fine — the named example is then a snapshot gap, and the real structural blind spot is a different, narrower one (e.g. cross-reference-only discovery with no keyword search). Distinguish the two: the named gap's root cause, and the class of gap that persists even live. (Earned 09-24: tracker assessment — committed absence was fixture-backed, live run discovered the PR 4×.)

- **Committed generated artifacts can be NON-REPRODUCIBLE from the committed state — run the generator's `--check` before trusting them.** A generated artifact set whose state file records a change-log from a PRIOR state (e.g. `changes=[WAITING→ACTIVE]` while already storing `watch_status=ACTIVE`) is non-idempotent: re-running from the committed state produces a different output (`changes=[]`), so `--check` FAILS on the clean tree even though the artifacts are internally coherent. The validator may not catch this — coherence checks (state↔tracker↔digest agreement) pass while reproducibility fails, and a workflow that runs generator-write-then-validate (not `--check`) silently overwrites the stale artifacts. Audit move: run `--check` against the clean committed tree; if it fails, the committed artifacts were generated from a state that isn't committed — regenerate from the committed state so the set is idempotent. Also: a first-run-after-merge normalization diff is GUARANTEED when the committed state's source mode (fixture) differs from the live run's mode (live) — one-time, self-heals, but expect it. (Earned 09-24: Copilot-built tracker audit — `--check` failed, validator passed, workflow didn't gate on it.)

- **Fixture-only coverage data must be marked and skipped in LIVE mode — synthetic artifact numbers 404 on the real API.** When a generator's fixture adds coverage clusters (closed/merged/stalled/needs-nudge paths) with synthetic artifact numbers (e.g. 200001+), those numbers do not exist on the real API: a live run fetches them and dies with HTTP 404. The fix is a `fixture_only` flag on the coverage clusters, skipped when no fixture data is loaded — and the flag must be threaded through EVERY consumer: the generator's cluster loop, the schema (allow the field), the validator's unknown-field check, and the digest's tracked-cluster count (live count excludes fixture-only). A validator that still expects the fixture count when live mode produces fewer fails the same way the generator did. (Earned 09-24: tracker live run — 404 on a synthetic issue number, then validator failures on the fixture-only clusters' headings and digest count, each fixed in turn.)

- **Mutation-test the VALIDATOR, not just the code under test — a validator that passes on corrupted input is toothless.** When auditing a validation layer, don't stop at "validators pass": introduce deliberate defects (weaken the schema + add a bogus field, set a wrong-but-internally-consistent status, remove a required field, break a link) and confirm the validator FAILS on each. Gaps found this way: a validator that delegates entirely to the schema never rejects unknown fields when the schema is weakened; a validator that checks internal coherence but never recomputes derived state (e.g. watch_status from activity windows) passes a wrong-but-consistent value. The mutation set is the audit's real coverage map — report which defects were caught and which passed. (Earned 09-24: 9 mutations, 7 caught, 2 gaps — schema-trust and no-recompute.)

- **The forensics/reversing suite on this host is the Kali docker image, not host packages (banked 09-21).** `kalilinux/kali-rolling` (122MB, pulled ~3 weeks ago) carries ghidra, radare2/rizin, volatility, yara, binwalk, foremost, sleuthkit, john, hashcat, metasploit. The host itself has only binutils (objdump, strings, readelf, nm, strace) + nmap/tcpdump — no gdb, no volatility3, no yara-python natively. For binary-level work on a plugin or artifact: `docker run --rm -v <dir>:/work kalilinux/kali-rolling <tool> <args>`. For reading plugin SOURCE, plain file reads suffice — the container is for binary-level work only. (User: "I do know I have data forensics software on there too... On the host, I mean" — the tooling is in the image, not the host.)

- `gh api search/issues` 404s here — always `gh search issues "term" --repo o/r`. One failed round-trip is cheap; don't burn it repeatedly.
- Don't re-file a duplicate; a dup label means the class is KNOWN — read the canonical ticket the dup points to.
- Session-specific workarounds are not evidence against the platform: a defect that recurs from a FRESH state is the bug; one caused by your own wedged state is not.
- Public writes are one-way doors: the investigation is read-only; filing/commenting happens only on explicit user word.
- A large refactor/agent-driven codebase cut is the classic amplifier: same class, wider exposure, known post-merge regressions. Name it as amplifier even when the user's instinct says "everything broke right then."
- Deliver verdict + one next action, not the whole scan. The user's bar is actionability (former process-feedback pro): the finding is only as good as the decision it enables.
- **A load-bearing finding is a HYPOTHESIS with a falsifiable prediction, not a verdict — humble on the inference, assertive on the evidence.** When a finding implies a mechanism is load-bearing (e.g. "if this one dependency is removed, the whole feature is write-only"), state it as a hypothesis the reader can confirm or refute in minutes: (1) the dated, named commit/PR that created the condition; (2) the current-state check (grep/log that proves it holds on main); (3) the exact re-add/restoration in the fix under review; (4) a falsifiable prediction (delete X → named tests go red → the mechanism is blind); (5) a one-command tight test that proves it. Do NOT declare the fix "doomed" or "unworkable" — that is a verdict the user does not want stated outright. Lay the evidence so the reader reaches the conclusion themselves, and close with a question ("is X load-bearing contract, or incidental?") rather than a claim about the PR's fate. The precision is what makes it impossible to ignore; the humility is what keeps it a question.
- **Prove a load-bearing hypothesis with a MUTATION TEST, not just a prediction.** When the falsifiable prediction is "delete X → named tests go red → the mechanism is blind," actually run it: (1) check out the fix's head, (2) run the suite green as baseline, (3) add the proposed regression test if one exists and confirm it passes, (4) comment out / stub the load-bearing branch (return an error instead of the real path), (5) re-run and record the exact fail set. The mutation turning the read/visibility tests red while the write-path tests stay green is the empirical proof — it converts "the mechanism is blind without X" from a claim into a measured result (e.g. 14 passed → 15 with the combination test → 4 failed with the branch removed, first failure the same KeyError documented on the pre-fix base). Restore the branch with `git checkout -- <file>` afterward. This is the difference between asserting a falsifiable prediction and demonstrating it — the user's bar is "we have the means to test it, so why not do it?"
- **A truncated `git log --numstat`/`--shortstat` view can FALSELY read as "no shave happened."** When a bounded `head -N` cut of a numstat walk shows only small recent commits, do NOT conclude the large refactor never happened — the big commits are older and got cut off. The authoritative source for a decomposition's figures is the MERGED-PR TITLES themselves (`gh pr view <N> --json title,additions,deletions,mergedAt,author`): maintainers state the before→after line counts in the title ("cli.py 4,835 → 3,959 lines"). If a prior landing cites specific line-count figures, verify them against the PR titles before marking them `[SPECULATION]` — a truncated local git view is not evidence the claim is wrong.
- **Dating a large refactor/shrink on a big repo — the commands that actually work.** `gh search prs --json additions,deletions` FAILS ("Unknown JSON field") and the REST pulls LIST endpoint (`gh api repos/O/R/pulls?state=closed`) omits diff stats — only the single-PR endpoint populates them. Working sequence: (1) get candidate numbers from `gh search prs "refactor" --merged --json number,title,closedAt,author`; (2) fetch stats per candidate with `gh pr view <N> --json additions,deletions,mergedAt,mergeCommit`; (3) full-history `git log --numstat`/`--shortstat` walks time out on large repos — use subject search (`git log --oneline --grep="refactor|shrink|schema diet" -i`) to find candidates, then bounded `git show <sha> --stat` to verify; (4) bound `git log -S '<symbol>'` to a single file path (`-- <file>`) — `--all` walks are the slow path; (5) the repo's own AGENTS.md often documents the decomposition ("Facade + siblings layout") — read it to identify the shrink's shape before git archaeology.
- **A steer that scopes OUTPUT is not a steer to STOP the investigation.** When the user says "don't bleed X into the comment" or "keep Y internal," they are constraining the deliverable's framing, not revoking the read-only search. Killing a running read-only git/gh search on such a steer destroys in-flight evidence and forces a cold restart. Distinguish: a scope/consent steer (keep findings internal, don't cite them publicly) → continue the investigation, quarantine the finding from the public artifact; a stop steer ("stop", "let it go", "don't do that") → halt. When ambiguous, pause and confirm rather than kill a read-only process — a read-only search is cheap to continue and expensive to restart.
- **The parent class can live in YOUR OWN evidence chain, not the vendor's tracker — when every observed failure traces to the measuring probe, the harness is the class, not the product.** A cluster measured through a defective instrument mis-frames the verdict: a probe whose stub block silently disables the mechanism under test (a lockless store), or whose instrumentation lags the mechanism's release, produces a coherent set of "green" (or false-red) observations that are entirely the harness's semantics. Before hunting upstream for a parent ticket, run the cluster through its deterministic control arm (a held-open case that MUST block, an unheld control that MUST acquire) — if the control fails or the observations are artifacts of stub semantics, name the harness as the parent class, fix the probe, and re-measure. The vendor's tracker is the second place to look, never the first when the evidence chain itself is suspect.
- **"Amid-the-fix" and "still-broken" are not contradictory — they answer different questions, and a good report states BOTH layers.** Platform repair velocity (merged class-fix stream since the amplifier event) and user relief (are the user's specific tickets fixed) are separate verdicts: a platform can be mid-repair at scale while the user's rig stays broken because none of the user's tickets have a merged fix yet. When lanes split on this (one says still-broken, one says amid-the-fix), the resolution is not a coin-flip — it is two layers of the same answer. State the platform layer and the user-relief layer explicitly, and let the action follow the user-relief layer (what the user can do now) while the platform layer sets expectations (repair is coming, not here).
- **Byte-verify the shipped artifact before trusting a cross-host failure — sha256 both ends.** A stale copy on the target host produces failures that read exactly like regressions in the code under test; comparing local and remote hashes first costs seconds and eliminates the whole class. Same rule in reverse: a receipt printed by a script that was NOT the bytes you tested is not a receipt. Full bundle-and-ship recipe for cross-contour verification: `references/minimal-import-bundle.md`.
- **Probe what the wrapper DERIVES FROM, not the product's name.** A wrapper that appends a suffix to its input (`path.with_suffix(name + ".lock")`) turns a probe aimed at the derived file into a probe of a different file (a lock's lock). When a held-resource probe reports "acquired" inside what should be a held region, check which path the wrapper actually touched before touching the implementation.
- **Cross-platform harness writes: explicit `encoding="utf-8"` always.** An omitted encoding on Windows Python < 3.15 falls back to the ANSI codepage (cp1252): a section sign becomes a lone `0xA7` byte — invalid UTF-8 — and a strict decoder's refusal ("file exists but could not be read") is the guarded behavior working, not the bug. A fresh harness write followed by "could not be read" = check your own write's encoding first.
- **Ground behavior-semantics assumptions in the official docs before improvising a test's correctness.** When a probe's validity depends on platform or tool semantics (lock APIs, decode behavior, tool-action contracts), consult the authoritative documentation first — the docs also settle contract questions outright (a documented "no such action" explains a session surface missing it, and the maintainer rationale is findable in the merged-PR stream).
