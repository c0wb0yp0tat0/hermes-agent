## SEAM-2 — DOES THE SUBSTRATE'S ERA END WHEN CONTEXT WINDOWS GROW HUGE? (Answered: no — the field keeps proving the opposite.)

**F2.1 — "YOUR 1M-TOKEN CONTEXT WINDOW IS NOT MEMORY" (Hindsight, 2026-07-22):** context window = working memory: resets every call; "a ten-million-token window that resets every session remembers exactly as much as a two-thousand-token one: nothing"; context rot measured by Chroma (18 frontier models, 30–50% accuracy drops BEFORE the documented limit; cliffs — fine at 32K, collapsing at 64K; worse when distractors resemble the answer — exactly the project-history-dump case); "you never actually escape memory by buying a bigger window. You just move the selection problem somewhere." Translation: the doc-chain's premise (the record must live OUTSIDE the window and be re-read on demand) is the field's standing answer to the window-growers; the RFC's bounded read IS the selection problem, done properly.

**F2.2 — EXPLICIT STATE OUTLASTS LONG CONTEXT — THE RFC'S THESIS, FIELD-PUBLISHED (arXiv 2611.02361, "Agent Memory as Rate-Limited Filtering"):** on an executable policy domain: models reading full logs fall from 72–86% (after 16 events) to 48–55% (after 256); a reasoning 120B trails the explicit-state reader by 4–10 points at 256–1,024 events; "the length beyond which explicit state outlasts long context grows with the reader" — but there is ALWAYS a horizon beyond which the store wins; retaining raw log lines without order errs toward 50%. A parsed-updates filter beats retrieval, model-kept ledgers, and Mem0. Translation: this is the read-restore's falsifier-and-proof in one: the field measures the exact crossover (state beats raw context beyond a reader-dependent horizon), and the doc-chain is the explicit-state side of the crossover. The RFC's long-session gate (300+ cycles) is the same class as the paper's 256–1,024-event horizon — the rig's own measurement of the same law.

**F2.3 — PRO-LONG: PROGRAMMATIC MEMORY, ARC-VALIDATED (arXiv 2607.20064):** complete structured interaction log + programmatic search: NetHack up to 2.2×, ARC-AGI-3 +18.0pp average across frontier models, up to 97.4% best@2, at 4.2–5.8× FEWER tokens than specialized harnesses. Translation: the "keep everything + read programmatically" design (the doc-chain's actual motion) is field-verified ON ARC — the very benchmark family Continual-ARC builds on — with the token efficiency the RFC's economics argument claims.

**F2.4 — THE COST CROSSOVER (arXiv 2603.04814):** long-context wins accuracy early but per-turn cost grows with context; a fact-memory system becomes cheaper after ~10 turns at 100K context, break-even decreasing as context grows. And arXiv 2610.24671: explicit memory shows no consistent advantage over raw-history RAG — retrieval is THE bottleneck both ways; "improving access to existing information may be at least as important as constructing richer explicit memory." Translation: the read (access) is the field's identified bottleneck — the RFC's read-restore direction is the bottleneck's fix, and the cost curve is on the substrate's side once sessions reach the lengths the rig actually runs (the 799× marathon).

## SEAM-3 — THE VERIFIER-BASED MEMORY CLASS (the scribe's identity, field-standardized)

**F3.1 — THE FIELD NOW HAS STANDARDS FOR EXACTLY THE SCRIBE'S SHAPE (PAM v1.0, portable-ai-memory.org; IETF draft-infantado-agent-memory-architecture):** PAM: typed memories with full provenance (platform/conversation/message refs, extraction method), content hashing for deterministic dedup, SHA-256 integrity checksums (RFC 8785 canonicalization), temporal lifecycle (validity/supersession/archival) — the doc-chain's provenance-origin + archive-before-stub as an interchange STANDARD. Translation: the rig's byte-verified scribe cells are an independent instance of an EMERGING STANDARD class; the RFC can cite PAM/IETF vocabulary for its provenance and authority claims.

**F3.2 — SIGNED-FACT MEMORY (emem.dev) AND HASH-CHAINED AUDIT (governedmemory):** emem: every write carries an Ed25519 signature — "proves who signed it and that the bytes did not change. It does not prove that the value is true" (fact vs trust separation — the study's quote-not-assert discipline); governedmemory: `verify_chain()` recomputes every event's hash and checks prev_hash linkage, catching in-place tampering. Translation: the scribe's byte-verify + the branch's shared-head protection are this class; the additions the field offers: signature-of-writer (who) and hash-chains (ordering) — cheap upgrades to the scribe's assert that would harden the "never lose what we shaped" record further.
